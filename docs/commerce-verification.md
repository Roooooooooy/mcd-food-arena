# 本人账号版技术验收

Task 4 将已实现的本人会话、券和结算接口打包为同源 Node 24 网页服务，并把账号表单移到页头默认关闭的原生折叠入口。券匹配和订单核心行为没有改动。

## 可复现命令

```bash
npm --userconfig=/dev/null ci --include=dev
npm --userconfig=/dev/null test
npm --userconfig=/dev/null run typecheck
npm --userconfig=/dev/null run build:commerce
VITE_PUBLIC_DEMO=true VITE_PUBLIC_COMMERCE=false npm --userconfig=/dev/null run build -- --base=/mcd-food-arena/
```

两种构建都默认输出 `dist/`，验收时可追加 `--outDir .private/commerce-dist` 或 `--outDir .private/pages-dist` 分开保存。`npm start` 固定服务入口旁的项目 `dist/`；上线必须使用本人账号构建，不能将 Pages 的子路径构建放到这个服务。

部署构建验收还需在仓库外的全新临时目录复制必要源码、public、构建配置及 package/lock 文件，然后在 `NODE_ENV=production` 下执行 Blueprint 的完整 `ci --include=dev && run build:commerce` 命令。不要复制或链接已有 node_modules，也不要使用仓库内子目录，否则 npm 脚本可能沿父目录借用 Vite，掩盖缺失开发依赖的问题。

## HTTP 和配置边界

`tests/commerce-deployment.test.ts` 使用真实 Fastify、临时文件及越界符号链接，仅替换外部 MCP 连接边界。覆盖：

- 本机 loopback 默认、Render 公共 HTTPS 回退、显式 Origin 优先，以及非法 PORT/HOST/Origin 的启动拒绝。
- 真实 HTML/JS/HEAD、静态缓存和 `nosniff`/`no-referrer`；网页及 API 仍执行原来源校验，不信任 `X-Forwarded-Host`。
- `/healthz` 仅 GET/HEAD 已匹配的路线可绕过浏览器来源校验，响应没有账号、cookie 或外部查询。路径前缀和编码的其他路线不能扩大这个豁免。
- 未知 API 保持 JSON 404；解码后的重复路径分隔符直接拒绝，编码 API/demo 缺失路径也不回退应用壳。应用壳只回退无扩展名的文档导航，资源缺失、普通 fetch 与 POST 不回退 HTML。
- 目录遍历、重复编码、反斜线、控制符、点文件、私有目录和越界符号链接的 GET/HEAD 均不公开文件。
- 缺少构建目录拒绝启动；提供的监听选项生效，测试仅监听系统分配的临时 loopback 端口。

静态实现只公开受限类型的构建文件，逐个检查 realpath 留在构建目录内；没有任意源码/私有目录服务器。`/assets/` 与内容哈希命名的冻结图片可缓存一年；HTML、目录 JSON 与所有账号 API 使用 `no-store`。静态目录是部署产生的可信、不可变文件，不支持用户上传。进程使用一个内存会话管理器；没有 cluster、多实例、DB 或共享 Token 后备。

既有 Task 1–3 测试继续验证各会话缓存与报价所有权、断开/过期、来源与编码路线限流、券绑定、数量/定制、晚到结果、单次报价提交及未确认状态。测试内的 `create-order` 使用假外部 gateway，不代表真实账号曾创建订单。

## UI 与运行验收分工

服务端渲染测试检查默认关闭的原生账号 disclosure、口令输入框、官方凭据链接、有效期/断开内容及键盘隔离标记；已加载菜单不再提示首次加载。手机视觉和浏览器焦点操作由主会话用 CUA 验证，包括 320/375px 的页头、打开账户、卡片、券详情、应用/撤销与报价修订。静态 HTML 测试不证明实际手机无溢出。

实现会话只进行假边界测试、类型检查、隔离构建和本机启动检查；没有读取真实 Token、调用真实 MCP、创建真实订单、注册/登录/连接 Render 或部署服务。主会话继续进行真实账号菜单、券详情和价格的只读验收，整分支审核及发布交接。完整命令输出、检查时点、提交 SHA 和仍未验证项记录在本地 Task 4 报告。

## 当前餐品可用性（Task 5）

本人菜单在进入当前对阵、进入结果页/改变餐盘以及点击“刷新可用状态”时核对。没有定时轮询或保活；门店菜单、实际详情和门店券来源在本人会话/菜单上下文内最多缓存 30 秒，并显示来源实际检查时间。冻结试玩不访问实时状态接口。

`POST /api/commerce/availability` 接收本人已注册的 `contextKey/candidateIds`（最多 200）；`POST /api/commerce/basket-availability` 接收 `contextKey/basket/cartRevision`。响应只包含餐品/选项公开身份、`listed/not-returned/unknown`、中文状态和时间，不能接收客户端 SKU、原始券号或库存覆盖。普通餐品缺席只有在成功、完整且分类引用与商品映射一致的菜单中才能成立。父商品派生的口味/杯型按实际父码、轮次和子项检查；券专用商品使用本人私有券映射、当前门店券与真实详情。

已确认未返回的餐品不能选择，相关图片灰显；名称、价格、规格和数量记录保留，可换规格、移出或重选。剩余候选重抽保留历史和淘汰池；只剩一份可选时与不可选候选配对，通过真实选择逐个淘汰。没有可选项时由用户跳过或调整。已完成结果不自动替换。手动、方向键、硬币提交都检查最新状态，硬币一侧确认不可选时禁用；飞行中拒绝结果后解除忙碌并复位。旧版本 2 存档能继续保存真实历史对阵及当前新对阵，无迁移。

下单前仍由官方 `calculate-price` 核价。报价前和创建前拦截已确认不可用的当前餐盘；创建阶段在重新核价后检查 30 秒来源新鲜度，再调用 `create-order`。价格失败不映射成不可用；失败/不完整来源为 `unknown`，不凭缺价格、特制能力、默认数量或随单购条件灰显食品。结果处每次可用性刷新开始即使新报价资格失效，已经创建或结果不确定的订单状态保留。

官方快餐工具当前没有可验证的精确库存数量或售罄原因。本功能只能证明当前菜单/选项/门店券返回情况，不能区分库存、时段、渠道或活动变化，也不能锁定库存。实现验证使用真实服务与假外部 MCP 边界；SSR 和纯状态测试不代替主会话的真实账号只读检查及浏览器动效、键盘/焦点和手机视觉验收。
